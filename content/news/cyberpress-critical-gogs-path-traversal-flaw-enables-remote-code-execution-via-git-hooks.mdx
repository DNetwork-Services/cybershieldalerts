A critical path traversal vulnerability in Gogs, the self-hosted Git service, could let authenticated attackers achieve remote code execution by planting malicious Git hooks outside the intended repository storage directory. Tracked as CVE-2026-52813, the flaw arises from an API endpoint that accepted unsanitized organization usernames and passed them to a filesystem path-construction routine. Aikido researcher Jorian Woltjer reported that the issue is fixed in Gogs 0.14.3. The finding underscores how small validation gaps in Git hosting software can combine with Git’s filesystem behavior to produce server-side code execution under the service account used to run Git operations remotely. Critical Gogs Path Traversal Flaw The vulnerable code used filepath.Join to append an organization name to the configured repository root. Although Gogs restricted ordinary user registrations to safe alphanumeric, dash, underscore, and period characters, its API organization-creation request did not apply equivalent validation. An attacker could therefore name an organization with ../ sequences, such as a traversal path targeting /tmp, then create a repository within it. Gogs would create the repository’s bare Git directory at that attacker-chosen filesystem location. Bare repositories normally contain metadata rather than a working copy, initially limiting the path traversal to a constrained file-write primitive rather than to arbitrary file replacement. Jorian Woltjer escalated that primitive by exploiting how Gogs creates temporary worktrees for web-based file editing. They created a legitimate editable repository, then used a traversal-named organization to place a malicious bare repository inside its temporary worktree. From a cloned copy of the legitimate repository, they committed a hook at traversal.git/hooks/update. Gogs’ web editor rejects paths containing .git/, but a normal Git push allowed the traversal.git path because its validation required a path segment named exactly .git. Gogs Path Traversal Flaw (Source: Aikido) A later API-driven commit to the nested repository invoked its update hook, running attacker commands as the git service user on the server successfully. The advisory also describes CVE-2026-52810, a separate authorization flaw in Gogs’ Git HTTP handling. The application determined whether a request was a read-only pull, in part, from a service query parameter, while routing the request by its path. Supplying service=git-upload-pack to a git-receive-pack The request caused the authorization layer to classify a push as a pull, potentially allowing a read-only collaborator to write to private repositories. Jorian Woltjer demonstrated the condition affected private repositories, or deployments configured to require sign-in before viewing repositories. A proposed correction normalizes the action and uses case-insensitive comparison, because an initial route-validation fix reportedly missed uppercase receive-pack paths in production. Gogs users should upgrade to 0.14.3 or later to address CVE-2026-52813 and review exposed instances for suspicious organizations, repositories, hooks, and unexpected filesystem paths. Administrators should also treat the receive-pack authorization bypass as unresolved until an upstream fix is available, especially where private repositories feed CI/CD pipelines. The notebook renderer issue further shows the attack surface: outdated notebookjs processed untrusted Jupyter Markdown through innerHTML, allowing event handlers to execute before server-side sanitization. The disclosures reinforce a defensive lesson for Git platform operators: validate every filesystem-derived identifier, separate authorization from routing, and prevent repository content from reaching executable hook locations. Give your security team the visibility and context to investigate suspicious activity faster and contain threats before business impact grows.
