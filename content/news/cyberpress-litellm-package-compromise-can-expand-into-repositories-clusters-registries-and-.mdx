A supply chain compromise involving LiteLLM highlights how a short-lived malicious package can create long-term risks across cloud environments, CI/CD systems, source-code repositories, Kubernetes clusters, package registries, and AI services. CloudSEK said the March 2026 campaign was linked to Team PCP and involved compromised releases of LiteLLM versions 1.82.7 and 1.82.8 on PyPI. The packages were reportedly available for around 40 minutes, but the impact window may be much longer because stolen credentials can remain valid after a malicious package is removed. The company’s reconstructed exposure dataset includes more than 2,500 organizations and approximately 434,000 potentially exposed CI/CD pipelines. However, inclusion in the dataset should not be treated as proof of compromise. It indicates that an organization may have been exposed to an affected package, pipeline, or credential path and should validate its environment privately. CloudSEK listed several major companies as high-confidence organization-level exposure matches. The classification refers to the strength of the match, not confirmed malicious execution, credential theft, or attacker activity. Organizations must investigate logs, pipeline histories, package downloads, and credential usage before determining whether an incident occurred. The risk comes from the permissions available to an affected process. A developer workstation or CI runner may contain cloud credentials, GitHub or GitLab tokens, SSH keys, Kubernetes service-account tokens, environment variables, registry credentials, database connections, and LLM API keys. If malware can access these items, attackers may move far beyond the initially compromised Python package. LiteLLM Breach Threatens Cloud According to the supplied incident details, the campaign began with the compromise of trusted security tooling. An automation token that was rotated but not fully revoked allegedly allowed attackers to force-push malicious code to published version tags of the Trivy scanner. LiteLLM’s CI pipeline reportedly installed Trivy without pinning it to a verified immutable version. The compromised scanner then entered the LiteLLM build process, leading to the publication of poisoned releases on PyPI. The malicious packages reportedly used a .pth file, which executes when the Python interpreter starts. This means the payload could run even if an application did not explicitly import LiteLLM. It also reduces the value of install-time protections such as --ignore-scripts, because .pth execution occurs during Python startup rather than package installation. Once active on a CI runner, the payload could search for credentials in environment variables, local files, process memory, cloud instance metadata services, and mounted Kubernetes service-account paths. The reported target data included AWS, Azure, and Google Cloud credentials; repository tokens; SSH keys; Kubernetes secrets; package publishing tokens; and AI-provider keys, cloudsek said. The report also states that stolen data was encrypted before being sent to attacker-controlled infrastructure. In cases where external exfiltration failed, the malware allegedly created public GitHub repositories in victim accounts and uploaded collected data as release assets.
