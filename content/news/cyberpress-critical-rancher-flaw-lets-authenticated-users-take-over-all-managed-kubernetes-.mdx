SUSE has fixed a critical privilege-escalation vulnerability in Rancher that could allow a low-privileged authenticated user to seize administrative control of the Rancher management plane and every downstream Kubernetes cluster it manages. Tracked as CVE-2026-44945 and GitHub advisory GHSA-v584-7w32-jwpq, the issue carries a CVSS v3.1 score of 9.1 and is classified as CWE-441, or an unintended proxy/confused-deputy weakness. The flaw resides in Rancher’s impersonation middleware, specifically pkg/auth/requests/impersonate.go. Rancher supports Kubernetes API impersonation by processing headers such as Impersonate-User, Impersonate-Group, and Impersonate-Extra-*. Critical Rancher Flaw However, the vulnerable implementation checked authorization in one Kubernetes cluster while ultimately sending the request to another: Rancher’s local management cluster. This creates a cross-cluster authorization mismatch. When a request arrived, Rancher parsed a cluster identifier from the URL and performed a Kubernetes SubjectAccessReview (SAR) against that specified downstream cluster. The request was then handled by Rancher’s management API, which uses the privileged scaledContext service account to operate against the local Rancher cluster. The Norman proxy store forwarded impersonation headers to that local Kubernetes API. An attacker could therefore control the authorization decision by choosing a downstream cluster where they hold RBAC privileges, while directing the effective action to the far more sensitive local Rancher management cluster. In practical terms, a user can arrange for their attacker-controlled downstream cluster to approve impersonation of a privileged identity, such as system:masters. Rancher’s management-plane API then honors that impersonation context when processing the request locally. The attack does not require existing access to a production cluster, a Rancher administrator role, or user interaction. Exploitation requires an authenticated Rancher session and control of RBAC in at least one registered downstream cluster. Because users assigned Rancher’s default user global role can generally import a cluster, an attacker could register a disposable k3d, kind, or minikube environment and use it as the authorization oracle for the escalation attempt. Successful exploitation can expose Rancher’s most sensitive control-plane assets. An attacker gaining local-cluster administrative access could read secrets holding downstream kubeconfigs, authentication-provider credentials, LDAP bind passwords, OIDC client secrets, and SAML signing keys. They could also create or modify GlobalRoleBindings, establish persistent administrative access, and use Rancher’s central management capabilities to compromise all enrolled downstream clusters. SUSE states that the flaw enables takeover of the control plane, managed clusters, and stored secrets. The patch changes the authorization boundary, so SAR-based impersonation checks are evaluated using a fixed client for the local Rancher management cluster, rather than a client selected from the request URL. The SAR middleware also now retrieves the authenticated identity from the request context instead of trusting supplied impersonation headers directly. Organizations should upgrade immediately to Rancher 2.14.4, 2.13.8, 2.12.12, or 2.11.16, as listed in SUSE’s security advisory. Teams unable to patch at once should restrict cluster-import permissions, review GlobalRoleBinding changes, audit privileged API activity, rotate potentially exposed credentials, and treat any suspicious Rancher management-plane access.
