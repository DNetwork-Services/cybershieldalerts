A newly disclosed CRLF header injection vulnerability, often treated as a low-impact flaw, can be exploited to enable HTTP request smuggling, response queue poisoning, cross-site scripting, and session cookie theft. Tom Stacey demonstrates that differences in how proxies, CDNs, and backend applications parse HTTP traffic can transform an injected newline into a critical desynchronization vulnerability. CRLF, short for carriage return and line feed, is the character sequence used to separate headers in HTTP messages. CRLF Header Injection Flaws If an application permits an attacker to introduce encoded CRLF characters, such as %0d%0a, into an input that is later decoded by a reverse proxy, the attacker may be able to alter the structure of the request forwarded to an upstream server. The research identifies Nginx configurations as a notable risk area. In particular, using variables such as $uri in a proxy_pass directive can cause Nginx to normalize and URL-decode attacker-controlled request paths before forwarding them to a backend. Hosted on the target CDN (Source: portswigger) This behavior may turn encoded CRLF sequences into real HTTP line breaks, enabling injected headers or even additional requests to be processed by the upstream service. The most severe outcome occurs when a frontend proxy and backend server disagree about request boundaries. Such parser discrepancies create HTTP request desynchronization, also known as request smuggling. A frontend may interpret traffic as one request while the backend interprets the same bytes as two requests. Attackers can exploit this mismatch to insert requests into another user’s connection stream, manipulate application behavior, or interfere with the order in which HTTP responses are delivered. Tom Stacey demonstrated CRLF-enabled CL.TE desync techniques, where conflicting Content-Length and Transfer-Encoding handling causes the frontend and backend to parse a request differently. They also showed request-splitting attacks that can lead to response queue poisoning. In this scenario, a server loses track of which response belongs to which client, potentially sending sensitive responses intended for legitimate users to an attacker-controlled connection. The study describes observed cases involving authentication tokens, session cookies, personally identifiable information, payment-related data, and internal service responses. In shared CDN or cloud environments, a desynchronization issue at the infrastructure layer can potentially affect multiple applications or tenants that depend on the same edge or proxy systems. self-replicating desync worm (Source: portswigger) A particularly concerning finding is that some CRLF desync attacks can be launched through ordinary browser behavior. If a malicious page persuades a victim’s browser to send a crafted request, the request may be issued using the victim’s authenticated session and network context. This expands the risk of connection-locked and IP-locked desync vulnerabilities, which might otherwise be difficult to exploit across users. The researchers also demonstrated a path to stealing HttpOnly cookies. Although the HttpOnly flag prevents JavaScript from directly accessing a cookie, a successful desync combined with XSS and response manipulation can expose a subsequent Set-Cookie header inside page content. Once the session token is rendered into the document, malicious script can read and exfiltrate it. Organizations should treat CRLF injection as a possible request-smuggling primitive, not merely a minor validation defect. Administrators should avoid unsafe Nginx proxy configurations involving $uri or $document_uri, reject encoded newline characters before proxy-routing logic, and assess parsing inconsistencies across CDNs, load balancers, reverse proxies, and origins. Tom Stacey also recommends adopting HTTP/2 for upstream connections as a more durable mitigation strategy.
